## ۱. خلاصه اجرایی

پروژه Persian NLP Pipeline یک پروژه پردازش زبان طبیعیِ سرتاسری برای تحلیل
نظرات فارسی کاربران دیجی‌کالا است. در این پروژه از مدل زبانی
ازپیش‌آموزش‌دیده ParsBERT استفاده شده که برای انجام دو وظیفه طبقه‌بندی متن
Fine-tune شده است:

۱. **پیش‌بینی وضعیت پیشنهاد محصول (Recommendation Prediction):** پیش‌بینی
اینکه نظر کاربر محصول را پیشنهاد می‌کند، پیشنهاد نمی‌کند یا وضعیت پیشنهاد
آن مشخص نیست.

۲. **پیش‌بینی بازه امتیاز (Rating Band Prediction):** پیش‌بینی یکی از سه
بازه `low`، `medium` یا `high` بر اساس متن نظر.

این پروژه بخش‌های مختلف چرخه توسعه یک سامانه یادگیری ماشین را پوشش می‌دهد؛
از آماده‌سازی داده‌های خام و Fine-tuning مدل گرفته تا ساخت سرویس استنتاج،
ارزیابی دسته‌ای، رابط کاربری و استقرار با Docker Compose.

ابزارهای اصلی پروژه شامل PyTorch، Hugging Face Transformers، FastAPI،
Gradio و Docker Compose هستند.

نتایج عددی تأییدشده‌ای که در این گزارش ارائه شده‌اند مربوط به Task A
هستند. فایل مدل Task B در پروژه وجود دارد، اما معیارهای ارزیابی تأییدشده
آن هنگام تهیه این گزارش در دسترس نبودند؛ بنابراین هیچ عددی برای عملکرد
Task B ادعا نمی‌شود.

## ۲. اهداف پروژه

اهداف اصلی پروژه عبارت‌اند از:

-   ایجاد یک فرایند قابل تکرار برای پیش‌پردازش و تقسیم مجموعه‌داده بزرگ
    نظرات فارسی.
-   Fine-tune کردن یک مدل زبانی فارسی برای طبقه‌بندی نظرات.
-   کاهش نشت اطلاعات در سطح محصول با تقسیم داده‌ها بر اساس شناسه محصول.
-   ارائه API برای اجرای استنتاج و ارزیابی.
-   پشتیبانی از ارزیابی دسته‌ای با استفاده از فایل‌های CSV.
-   آماده‌سازی پروژه برای استقرار قابل تکرار با Docker Compose.

## ۴. آماده‌سازی داده‌ها

فرایند پیش‌پردازش در نوت‌بوک زیر پیاده‌سازی شده است:

`notebooks/02_preprocessing_and_split.ipynb`

### ۴.۱. نرمال‌سازی متن فارسی

در این مرحله از نرمال‌ساز کتابخانه Hazm به همراه چند تبدیل تکمیلی و قطعی
استفاده شده است:

-   تبدیل حروف عربی `ي` و `ك` به حروف فارسی `ی` و `ک`.
-   تبدیل ارقام فارسی و عربی به ارقام ASCII.
-   حذف URLها و محتوای HTML.
-   نرمال‌سازی فاصله‌های افقی، با حفظ کاراکترهای خط جدید.
-   حفظ نیم‌فاصله (ZWNJ)، ایموجی‌ها و عبارت‌های منفی‌ساز.

برای تابع نرمال‌سازی، آزمون Idempotence نیز اجرا شد. در ۹ مورد آزمایش‌شده،
هیچ نقضی مشاهده نشد؛ یعنی اجرای مجدد نرمال‌سازی روی متن نرمال‌شده، تغییر
جدیدی ایجاد نکرد.

### ۴.۲. پاک‌سازی و آماده‌سازی ویژگی‌ها

مراحل پاک‌سازی شامل موارد زیر است:

-   تبدیل مقادیر متنی جایگزین مانند `"nan"`، `"null"` و `"None"` به
    مقدار Null واقعی در فیلدهای مرتبط.
-   حذف شناسه‌های تکراری نظر.
-   حذف ستون‌های فراداده‌ای که در فرایند آموزش استفاده نمی‌شوند.
-   نگه‌داشتن متن نظر، شناسه‌ها، برچسب پیشنهاد، امتیاز و فیلدهای مشتق‌شده
    مربوط به بازه امتیاز.

پس از حذف رکوردهای تکراری، تعداد 6,149,834 نظر باقی ماند.

### ۴.۳. ساخت بازه‌های امتیاز

فیلد عددی `rate` به سه کلاس دسته‌ای تبدیل شده است:

  بازه امتیاز            کلاس
  ---------------------- ----------
  `0 <= rate < 2.5`      `low`
  `2.5 <= rate < 4.0`    `medium`
  `4.0 <= rate <= 5.0`   `high`

امتیازهای خارج از بازه مجاز یا مقادیر Null به‌عنوان نامعتبر علامت‌گذاری
می‌شوند. در داده‌ها یک رکورد با مقدار امتیاز نامعتبر شناسایی شد.

## ۵. تقسیم داده و جلوگیری از نشت اطلاعات

### ۵.۱. تقسیم‌بندی گروهی بر اساس محصول

برای کاهش نشت اطلاعات میان داده‌های آموزش و ارزیابی، تقسیم‌بندی در سطح
**محصول** انجام شده است، نه در سطح تک‌تک نظرات.

محصول‌ها با استفاده از کلاس غالب وضعیت پیشنهاد در نظرات مربوط به هر
محصول، طبقه‌بندی و سپس تقسیم شده‌اند. نسبت تقسیم‌بندی به این صورت است:

-   ۷۰ درصد آموزش
-   ۱۵ درصد اعتبارسنجی
-   ۱۵ درصد آزمون

تعداد رکوردهای حاصل در هر بخش:

  بخش                     تعداد نظرات
  --------------------- -------------
  داده آموزش نظارت‌شده       3,578,692
  داده اعتبارسنجی             913,570
  داده آزمون                  919,841

آزمون عدم هم‌پوشانی شناسه محصولات با موفقیت انجام شد؛ هیچ `product_id`
مشترکی میان مجموعه‌های آموزش، اعتبارسنجی و آزمون وجود ندارد.

### ۵.۲. داده‌های آموزش نیمه‌نظارتی

یک فرایند Masking قطعی روی بخش آموزش نظارت‌شده اعمال شده است:

-   نرخ Masking: برابر با ۲۰ درصد
-   Seed: `digikala-semi-supervised-v1`
-   روش انتخاب: استفاده از هش پایدار SHA-256 مبتنی بر شناسه هر رکورد،
    به‌صورت جداگانه در هر کلاس

خروجی این مرحله:

  فایل آموزش                       تعداد رکورد

  `train_pseudo_unlabeled.csv`         737,731

برچسب رکوردهای Mask‌شده حذف شده و این نمونه‌ها به‌صورت متنِ بدون برچسب در
فایل `train_pseudo_unlabeled.csv` ذخیره شده‌اند. این دو فایل در کنار

همچنین فایل `natural_unlabeled.csv` شامل 627,763 رکورد است که برچسب

## ۶. Tokenization

Tokenizer از مدل پایه ParsBERT بارگذاری شده است:

[ParsBERT v2.0 ---
HooshvareLab](https://huggingface.co/HooshvareLab/bert-fa-base-uncased)

تنظیمات اصلی:

  تنظیم              مقدار
  ------------------ ---------------------------
  Tokenizer          توکنایزر ParsBERT v2.0
  اندازه واژگان      100,000
  حداکثر طول توالی   128
  روش Padding        پویا (Dynamic Padding)
  Collator           `DataCollatorWithPadding`

حداکثر طول توالی پس از بررسی توزیع طول توکن‌ها انتخاب شده است. در نمونه‌ای
شامل ۵۰۰۰ رکورد، صدک ۹۹ طول توکن‌ها تقریباً ۶۴ بود و تنها ۰.۰۸ درصد
نمونه‌ها به حداکثر طول تعیین‌شده یعنی ۱۲۸ توکن رسیدند.

Tokenization از طریق کلاس `ReviewDataset` انجام می‌شود. برای جلوگیری از
Padding غیرضروری، طول نمونه‌ها در زمان تشکیل Batch تنظیم می‌شود، نه اینکه
تمام نمونه‌ها از ابتدا تا طول ۱۲۸ Padding شوند. در موارد لازم، برچسب‌های
ناموجود با مقدار `-100` مشخص می‌شوند تا در محاسبه Loss نادیده گرفته شوند.

## ۷. معماری مدل و Fine-tuning

### ۷.۱. مدل پایه

هر دو وظیفه از مدل ParsBERT v2.0 استفاده می‌کنند:

-   مدل: `HooshvareLab/bert-fa-base-uncased`
-   معماری: BERT-base
-   تعداد لایه‌های Transformer: ۱۲
-   اندازه لایه پنهان: ۷۶۸
-   تعداد Attention Head: دوازده
-   تعداد پارامترهای مدل طبقه‌بندی: تقریباً ۱۶۲.۸ میلیون

مدل‌های طبقه‌بندی با استفاده از کلاس `AutoModelForSequenceClassification`
در کتابخانه Hugging Face ساخته شده‌اند.

### ۷.۲. وظیفه اول --- پیش‌بینی وضعیت پیشنهاد محصول (Task A)

Task A یک مسئله طبقه‌بندی سه‌کلاسه است:

-   `recommended`
-   `not_recommended`
-   `no_idea`

تنظیمات آموزش شامل موارد زیر است:

-   تابع Cross-Entropy با وزن‌دهی معکوس فراوانی کلاس‌ها.
-   بهینه‌ساز AdamW با نرخ یادگیری جداگانه برای Encoder و Classification
    Head.
-   نرخ یادگیری Encoder برابر با `2e-5`.
-   نرخ یادگیری Classification Head برابر با `1e-4`.
-   زمان‌بند خطی نرخ یادگیری با ۱۰ درصد Warmup.
-   Batch Size برابر با ۱۶ و Gradient Accumulation برابر با ۲؛ در نتیجه
    Batch Size مؤثر ۳۲ است.
-   حداکثر طول توالی برابر با ۱۲۸.
-   آموزش با Mixed Precision و فعال بودن `fp16`.
-   مقدار Weight Decay در آزمایش نهایی برابر با `0.05`.
-   انتخاب مدل بر اساس Macro F1 مجموعه Validation.

وزن کلاس‌ها در آزمایش دارای Loss وزن‌دهی‌شده:

  کلاس                   وزن
  ------------------- ------
  `recommended`         0.42
  `not_recommended`     3.49
  `no_idea`             2.96

### ۷.۳. آزمایش‌های Task A

چند پیکربندی مختلف برای آموزش بررسی شده‌اند:

  آزمایش   پیکربندی                  بهترین Macro F1 گزارش‌شده در Validation
  -------- ----------------------- ----------------------------------------
  v1       بدون وزن‌دهی کلاس‌ها                                         0.677
  v3       Loss با وزن‌دهی کلاس‌ها                                      0.693
  v5       پیکربندی بازنگری‌شده                                        0.702

**نکته مهم درباره Checkpoint:** بهترین Macro F1 مشاهده‌شده در آزمایش v5
برابر با 0.702 و مربوط به گام 10,000 بود. این Checkpoint به دلیل محدودیت
نگه‌داری Checkpointها ذخیره نماند. مدل نهایی ذخیره‌شده مربوط به Checkpoint
گام 4,000 است و نتایج ارزیابی آن در بخش بعد آمده است. بنابراین نباید
بهترین امتیاز مشاهده‌شده در طول آموزش را با عملکرد مدل نهایی ذخیره‌شده
یکسان در نظر گرفت.

مدل نهایی ذخیره‌شده برای Task A با نتایج زیر ارزیابی شده است:

  معیار                  مقدار
  ------------------- --------
  Accuracy              0.8361
  Balanced Accuracy     0.7141
  Macro F1              0.6941

### ۸.۱. نتایج هر کلاس

  کلاس                  Precision   Recall   F1-score
  ------------------- ----------- -------- ----------
  `recommended`             0.951    0.894      0.922
  `not_recommended`         0.721    0.678      0.699
  `no_idea`                 0.388    0.570      0.462

### ۸.۲. تحلیل نتایج

بهترین عملکرد مدل مربوط به کلاس `recommended` است. مقدار Precision و
Recall این کلاس هر دو بالا هستند؛ بنابراین مدل این کلاس پرتکرار را با
اطمینان مناسبی تشخیص می‌دهد.

عملکرد مدل برای کلاس‌های `not_recommended` و به‌ویژه `no_idea` ضعیف‌تر است.
کلاس `no_idea` کمترین Precision را دارد که نشان‌دهنده میزان قابل توجهی از
اشتباه مدل در تشخیص این کلاس و تمایز آن از کلاس‌های دیگر است. این موضوع
یکی از محدودیت‌های مهم مدل برای تحلیل خودکار نظرات محسوب می‌شود.

با توجه به نامتوازن بودن توزیع کلاس‌ها، Accuracy به‌تنهایی معیار کافی برای
توصیف عملکرد مدل نیست. معیارهای Balanced Accuracy و Macro F1 اطلاعات
بیشتری درباره عملکرد مدل روی تمام کلاس‌ها ارائه می‌کنند.

کند:

-   `low`
-   `medium`
-   `high`

## ۱۰. سرویس استنتاج (Inference API)

سرویس استنتاج با استفاده از FastAPI و Uvicorn پیاده‌سازی شده است.

فایل اصلی:

`src/persian_nlp_pipeline/api.py`

Endpointهای تعریف‌شده:

  Endpoint                          متد    کاربرد
  --------------------------------- ------ ------------------------------------
  `/health`                         GET    بررسی سلامت سرویس
  `/api/v1/predict`                 POST   اجرای پیش‌بینی
  `/api/v1/evaluate`                POST   ارسال فایل CSV برای ارزیابی دسته‌ای
  `/api/v1/evaluation/{filename}`   GET    دریافت خروجی ارزیابی

منطق پیش‌بینی و ارزیابی در ماژول‌های جداگانه‌ای مانند `predictor.py` و
`evaluator.py` قرار گرفته است.

## ۱۱. ارزیابی دسته‌ای (Batch Evaluation)

بخش Batch Evaluation فایل CSV را دریافت کرده و استنتاج را به‌صورت دسته‌ای
روی رکوردها اجرا می‌کند. مراحل اصلی این فرایند عبارت‌اند از:

۱. خواندن فایل CSV ورودی.\
۲. اجرای استنتاج مدل روی نظرات.\
۳. محاسبه معیارهای ارزیابی، در صورت وجود برچسب واقعی.\
۴. تولید Confusion Matrix و خروجی پیش‌بینی‌ها.\
۵. ذخیره فایل‌های خروجی در مسیر `artifacts/evaluation/`.

این قابلیت امکان ارزیابی مدل روی مجموعه‌داده‌های خارجی را بدون نیاز به
اجرای دستی سلول‌های Notebook فراهم می‌کند.

## ۱۲. رابط کاربری Gradio

رابط کاربری در فایل زیر پیاده‌سازی شده است:

`frontend/app.py`

Gradio یک رابط تعاملی برای ارسال متن نظر و مشاهده خروجی مدل فراهم می‌کند.
این رابط از طریق متغیر محیطی `API_URL` با Backend مبتنی بر FastAPI
ارتباط برقرار می‌کند.

مقدار پیش‌فرض URL برای توسعه محلی تنظیم شده است و در اجرای Docker
Compose، آدرس سرویس Backend به‌صورت متناسب با شبکه داخلی کانتینرها تنظیم
می‌شود.

## ۱۳. استقرار با Docker

فایل‌های مرتبط با استقرار شامل موارد زیر هستند:

-   `Dockerfile`
-   `docker-compose.yml`
-   `.dockerignore`
-   `pyproject.toml`
-   `uv.lock`

Docker Compose دو سرویس اجرا می‌کند:

  سرویس      کاربرد                       پورت
  ---------- -------------------------- ------
  API        Backend مبتنی بر FastAPI     8000
  Frontend   رابط کاربری Gradio           7860

هر دو سرویس از Image پروژه استفاده می‌کنند، اما فرایندهای اجرایی
جداگانه‌ای دارند. برای سرویس‌ها Health Check تعریف شده و از Bind Mount
برای ماندگاری فایل‌های خروجی ارزیابی استفاده می‌شود.

### ۱۳.۱. اجرای سریع پروژه

ابتدا مخزن را Clone و سرویس‌ها را اجرا کنید:

``` bash
git clone https://github.com/ItsJavadHosseini/persian-nlp-pipeline.git
cd persian-nlp-pipeline
docker compose up -d
```

سپس از آدرس‌های محلی زیر استفاده کنید:

  سرویس          آدرس
  -------------- ------------------------------
  رابط Gradio    http://localhost:7860
  API            http://localhost:8000
  مستندات API    http://localhost:8000/docs
  Health Check   http://localhost:8000/health

برای متوقف کردن سرویس‌ها:

``` bash
docker compose down
```

## ۱۶. محدودیت‌ها و مسیرهای توسعه آینده

موارد زیر می‌توانند در نسخه‌های بعدی پروژه بررسی و بهبود داده شوند:

۱. **بهبود عملکرد روی کلاس‌های اقلیت:** بررسی خطاهای هر کلاس، آزمایش
تابع‌های Loss جایگزین، نمونه‌برداری مجدد و تنظیم آستانه تصمیم؛ به‌ویژه برای
کلاس `no_idea`.

۲. **نگه‌داری Checkpoint برتر:** تنظیم سیاست ذخیره Checkpoint یا ذخیره
صریح بهترین مدل بر اساس معیار Validation تا بهترین مدل مشاهده‌شده در طول
آموزش از دست نرود.

۳. **تکمیل ارزیابی Task B:** ثبت معیارهای Validation و Test، مقادیر
Precision/Recall/F1 هر کلاس و Confusion Matrix.

۴. **ارزیابی روی داده مستقل:** بررسی پایداری مدل روی نظرات مربوط به بازه
زمانی متفاوت یا منبع داده دیگر.

۵. **افزودن تست‌های خودکار:** پوشش نرمال‌سازی متن، اعتبارسنجی داده، ساختار
خروجی پیش‌بینی، رفتار API و Batch Evaluation.

۶. **مدیریت آزمایش‌ها:** ثبت منظم پیکربندی مدل‌ها، Checkpointها، معیارها و
نسخه‌های مجموعه‌داده در یک سامانه مدیریت آزمایش.

۷. **مستندسازی توزیع مدل‌ها:** مدل‌های Fine-tune‌شده در حال حاضر به‌صورت
محلی در مسیرهای Artifact پروژه ذخیره شده‌اند و صفحه عمومی در Hugging Face
ندارند.

## ۱۸. جمع‌بندی

پروژه Persian NLP Pipeline یک چرخه کامل توسعه کاربردی NLP را پیاده‌سازی
می‌کند: پیش‌پردازش حجم بالایی از نظرات فارسی، تقسیم‌بندی داده با در نظر
گرفتن شناسه محصول، Fine-tuning مدل ParsBERT، ارزیابی، توسعه API، ساخت
رابط کاربری تعاملی و استقرار مبتنی بر Docker.

مدل نهایی ذخیره‌شده برای Task A به Accuracy برابر با **0.8361**، Balanced
Accuracy برابر با **0.7141** و Macro F1 برابر با **0.6941** دست یافته
است. نتایج تفکیک‌شده کلاس‌ها نیز نشان می‌دهند که بهبود عملکرد روی کلاس‌های
اقلیت، به‌ویژه `no_idea`، یکی از مهم‌ترین مسیرهای توسعه بعدی است.

این پروژه یک زیرساخت قابل استقرار برای طبقه‌بندی نظرات فارسی کاربران
فراهم می‌کند. در ادامه، بهبود عملکرد کلاس‌های اقلیت، نگه‌داری بهترین
Checkpoint آموزش و تکمیل ارزیابی مستند Task B از اولویت‌های اصلی توسعه
خواهند بود.
